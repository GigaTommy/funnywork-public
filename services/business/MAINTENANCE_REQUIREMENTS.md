# 需求池与影响分析

管理端入口：任务中心 → 需求池。新需求仍进入既有后端产品、技术、派发、审查与验收流程，不新增执行器或逐单管理员审批。本地安全、归并、权限链与跨工作台复核记录按[贡献指南](../../CONTRIBUTING.md#配置与数据)归档。

## 需求管理

- 需求有独立 ID、优先级、修订号、期望行为、涉及路径、稳定验收条件 ID。每次保存形成不可变修订，编辑需提供当前版本；新验收条件由后端分配 ID，不能引用其他需求的编号。
- 手工需求先进入待梳理状态，保存不会创建执行任务。“开始审查”幂等关联同一条受理记录；创建接口也使用请求键防止响应丢失造成重复需求。当前优先级在尚未检查的同批候选间排序，最近检查时间优先轮转，避免高优先级阻塞项长期占满队列。
- 产品 Agent 接受反馈后、技术可行性分析前保存独立需求。因此技术分析阻塞或要求补资料时，产品需求不会消失。重新分析尚未派发的反馈形成新修订；已关联执行的需求不覆盖历史规格。
- 手工需求待补资料、暂不开发或延期且没有关联执行、没有正在运行的审查时，可编辑同一需求并生成新修订，重新排入同一受理记录。已派发产品意图冻结，后续变化需新建需求或走已有返工流程。
- “导入已有分析”按授权范围每批最多 100 条整理历史受理结果；缺少明确需求和验收条件的记录计为跳过。历史导入不调用模型、不创建执行、不重写旧规格或伪造旧验收映射。
- 管理详情包含来源、分析阶段与阻塞原因、修订记录和执行关联。反馈与执行下钻保留返回需求的路由上下文。管理端创建的需求来源不混入桌面用户的 CLIENT 反馈列表。

## 产品与验证映射

产品输出可按独立行为生成 `acceptanceCriteria`；修订相同行为可引用本需求既有 ID，新行为使用空 ID，由服务端生成。旧产品结果只有验收文本时，保留原文为一个条件，不自动推断其内部结构。

技术输出的每个 SAT/UAT 条件必须提供 `productCriterionIds`，引用已冻结的产品条件。每个涉及验证的平台均需覆盖每项产品条件的 SAT 和 UAT；漏项、外来编号会使技术阶段重试或阻塞，不能进入派发。

执行规格的 `product` 字段冻结需求 ID、修订、产品条件、技术验证映射及影响分析 ID；派发审批摘要包含这些字段。原 `acceptance` 继续提供产品条件原文，技术计划保留在独立部分。已有无 `product` 的执行规格继续按原协议读取，不追补未经验证的映射。

## 影响分析

分析复用固定 Git 基线的真实文件清单和源码采样，不额外调用模型：

1. 按需求路径识别直接组件；没有配置的已观察文件按目录分组，平台标为未知。
2. 按管理员维护的组件依赖向使用方计算传递影响。依赖可跨桌面、手机、管理端与服务端；平台来自显式配置，不能据此声称客户端已验证。
3. 从当前采样源码中识别受支持的字面量相对引用，关联清单中的目标文件，保留来源文件及目标路径作为依据。
4. 技术分析先读取产品范围影响；计划完成后再按具体计划路径保存影响结果，冻结其 ID。分析记录区分 `PRODUCT_SCOPE` 与 `TECHNICAL_PLAN`。

影响组件列表用于识别风险，不自动扩大允许改动路径，也不创建新的移动端执行器。自动执行与验证按已配置的 Mac／Windows 策略调度；涉及 iOS／Android 的改动需在对应工具链和设备上验证。

结果保留基线 SHA、路径、组件、传播边、文件及采样数量、未找到路径和未验证项。当前最多 200 个清单文件、8 个源码采样、48 KB，依赖边达到 8000 条时停止增加源码引用并标出缺口；源码引用识别不是完整语义依赖解析，不覆盖动态导入、服务运行时调用和任意语言的依赖。分析结果标记为部分证据；未观察到的依赖通过组件配置和人工检查补充。

需求修订、受理范围或组件依赖变化后，旧分析标为过期；网络读取期间变化会拒绝保存。自动派发前再次核对需求版本和影响配置摘要。基线 SHA 固定分析使用的提交；重新分析前核对远端分支并获取新基线。

## 接口与权限

所有路径位于 `/api/v1/maintenance`。管理身份桥分别检查 tasks / agents 的读写权限；业务服务重新校验当前 OPERATOR、租户及仓库区域。组件依赖写入另需 ADMIN。

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/requirements` | 标题、仓库、状态筛选和游标分页，授权过滤在 LIMIT 之前 |
| GET | `/requirements/catalog` | 可用项目、路径范围与默认平台，不返回凭据引用 |
| POST | `/requirements` | 新建草稿，必需 `Idempotency-Key` |
| GET / POST | `/requirements/{id}` | 详情 / 乐观版本编辑 |
| POST | `/requirements/{id}/queue` | 将冻结修订交给已有自动审查流程 |
| POST | `/requirements/{id}/impact` | 基于固定基线分析，携带 expectedVersion |
| POST | `/requirements/import?after=` | 分批导入历史分析，返回 imported / skipped / nextCursor |
| GET / POST | `/requirement-dependencies/{repositoryId}` | 查看 / 乐观版本保存结构化组件依赖 |

需求列表使用稳定游标，查询失败保留原页。详情展示最近 10 次影响分析；完整分析记录仍保留在数据库。修改未保存时切换工作台会提示；成功写入后的读取失败单独提示，避免误报写入失败。权限失效清除列表、详情及编辑草稿。

## 升级与验证

需求池依赖业务数据库 V122–V124 迁移，分别提供需求与修订、检索索引及补资料暂缓标记。升级前备份业务数据库，启动新业务服务并确认迁移成功，再发布配套管理前端。回退应用版本时保留新增表及数据；删除表前先归档需求与修订。

页面交互夹具与运行命令见[需求池测试入口](../../apps/management/uat/requirements/README.md)。使用隔离账号验证创建、编辑冲突、入队幂等、补资料恢复、影响分析失效、权限撤销与分页。模型分析及仓库派发使用专用测试需求，分别核对需求修订、冻结规格、执行关联和服务端检查结果。
