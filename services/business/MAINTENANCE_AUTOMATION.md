# 后端 Agent 自动维护运行参考

本文描述后端自动维护的执行职责、启用条件、验证政策和故障恢复。仓库与客户端接入见[维护配置](MAINTENANCE.md)，账号、设备和项目授权分别由相应管理模块维护。

## 运行路径

客户端反馈与 GitHub Issue → 后端需求／产品 → 只读基线和技术方案 → 冻结验收条件 → 既有任务通道 → 原 Mac／Windows 内置 Agent 开发和提交候选 → 后端获取远端实际 diff 独立审查 → 既有 VERIFY 通道执行固定 SAT／UAT → 后端产品验收 → 核验 CI、来源和远端版本 → 后端合并、回告及关闭。

后端模型调用复用模型中间层的许可、预算和计量，支持 Messages 和 Chat Completions。各角色使用独立请求上下文，审查读取实际候选代码及验证结果。管理员配置项目政策并检查结果，自动流程按政策运行。

执行前配置项目／用途授权、资源池和路由，见[执行资源协议](EXECUTION_RESOURCES.md)及[管理配置](EXECUTION_RESOURCES_R4.md)。空授权任务等待配置；设备绑定与项目授权分别维护。COMPILE 用途编制固定模板[经营摘要](ANNUAL_REPORTS_R5.md)。

## 阶段与运行条件

| 阶段 | 运行行为 | 使用条件 |
| --- | --- | --- |
| 需求／产品和技术 | PRODUCT、SECURITY、BASELINE、TECHNICAL、DISPATCH 持久阶段；结构化需求、范围与 SAT／UAT 条件 | 验收命令仍需项目预先配置；不足时补资料，不允许反馈指定任意执行命令 |
| 恶意反馈 | 独立安全复判、原文证据、来源事件幂等；7 日内 3 次确认攻击后限制 7 日；后续受限反馈不消耗模型 | 限制作用于维护反馈，账号登录和付费权益保持原状态；申诉由运营人员核查 |
| 原客户端开发测试 | 原任务租约、设备绑定、内置 Agent、固定候选 VERIFY；SAT/UAT 用例关联条件 | 办公机结果按 CLIENT_REPORTED 保存，终端按组织设备安全要求管理 |
| 后端独立审查验收 | 直接读取真实 PR、范围、文件模式、完整 patch；独立代码审查和逐条件自动验收 | 审查使用后端读取的 PR 和已记录的客户端验证结果；可信执行证明需由部署环境另行提供 |
| 后端交付 | 固定 SHA、规定 GitHub Actions 检查成功、源状态核对、普通合并 API；动作台账与超时对账 | APP_ISOLATED 要求独立 App 身份与分支保护；开发单账号模式按下文显式配置 |
| 管理交互 | 展示归并来源、三职责、阶段详情／输入、开发及验证任务导航、SAT／UAT、自动验收和交付回执；隐藏自动任务的人工批准按钮 | 各平台的完整执行需在对应环境验证 |

项目检查补强后，后端技术角色必须重新审查冻结的原始条件和新命令，才更新计划摘要并创建全新验证任务。不得删除原平台／必需 CI；旧结果归档且不能抵作新计划通过。没有已批准新计划时保持阻塞，不直接改写为通过。

后台阶段有租约和有限重试，未知模型执行结果阻塞；已收到停止后的 RUNTIME_FAILED 回执，由恢复 Agent 有界判断是否按原冻结范围重试（最多第 4 版），不自动提高预算或权限；等待外部条件释放模型，不常驻三个模型 loop。CI 未结束每 30 秒对账，最长等待 24 小时，不消耗模型或三次失败额度；明确失败拒绝交付。验证执行收到确定的 RUNTIME_FAILED 回执可有限重试，原始失败、任务及摘要归档；未知执行和实际 CHECKS_FAILED 不自动当作基础设施失败重试。仅自动处理政策启用后自动受理的需求，不追溯合并历史人工任务。

## 统一账号开发配置

私有仓库的开发试点可显式配置单账号模式。以下示例使用 `GigaTommy`，部署时替换为实际授权的 GitHub 登录名：

```text
FUNNYWORK_MAINTENANCE_SINGLE_ACCOUNT_DEVELOPMENT=true
FUNNYWORK_MAINTENANCE_DEVELOPMENT_GITHUB_LOGIN=GigaTommy
```

自动化策略 `identityMode=SINGLE_ACCOUNT_DEV`，`environmentPolicy` 固定为 `DEVELOPMENT_FUNCTIONAL`。三个 tokenRef 可指向相同的服务端环境变量名称；凭据本身不写入 API、需求、模型或文档。检查实际 GitHub 登录名、私有仓库和写权限；身份不符拒绝交付。普通合并仍遵守 GitHub 上实际存在的规则，不强推、不使用管理员绕过。

该模式不提交 GitHub 自审批准：同一账号不能批准自己的 PR。后端独立审查与产品验收仍必须通过。单账号开发模式使用同一 GitHub 身份和仓库实际规则。需要独立身份与分支保护的部署使用默认 `APP_ISOLATED`，并预先完成 App 安装与权限配置；缺少条件时拒绝交付。

## 接口和兼容

| 接口 | 用途 |
| --- | --- |
| `POST /api/v1/maintenance/automation/policies` | ADMIN 配置 repositoryId、deploymentId、enabled、autoMerge、readTokenRef、deliveryTokenRef、reviewerTokenRef、identityMode |
| `GET /api/v1/maintenance/automation/stages/{id}` | OPERATOR 在租户及区域权限内查看单阶段固定输入、结果和错误 |
| `GET /api/v1/maintenance/automation` | OPERATOR 查看有权仓库的政策、阶段及风险事件 |
| `PUT /api/v1/maintenance/repositories/{id}/checks` | ADMIN 更新项目默认检查；运行中任务拒绝变更；新任务冻结新规格 |
| `GET /api/v1/maintenance/automation/problems/{id}/evidence` | 查看绑定需求、候选、验收条件、后端阶段与交付动作的证据封装 |
| 原 `/api/account/sync/feedback`、Issue 增量同步 | 保持来源入口；对客户端隐藏内部方案和其他来源文本 |
| 原设备任务交换、维护结果回传、VERIFY | 保持原客户端兼容；启用自动化后拒绝旧客户端 DELIVER 和人工决定旁路 |

`V107` 增加政策、阶段、风险、限制、动作与验收条件；`V108` 增加身份模式；`V109` 保留验证任务失败及被替换计划的完整历史，不修改已发布迁移。政策变更增加 revision，运行中阶段拒绝改政策。

证据逻辑版本 `funnywork.maintenance.evidence/v1`，封装摘要使用当前后端规范化 JSON；`origin=BACKEND_OBSERVED`、`attestationAvailable=false`，客户端原始结果明确标注 CLIENT_REPORTED。digest 用于核对封装内容；可信执行证明字段为 false，验证方按客户端来源处理原始结果。

产品规范写入所有后端角色规则：菜单简短清晰；需求及产品说明不直接作为宣传文案；技术保留边界不泄漏到客户手册；引用的攻击文本是数据。独立审查检查实际改动，异常反馈不直接写长期记忆。

## 执行资源管理

执行资源页面提供配置、只读候选预览和排除原因；任务详情显示实际执行终端。菜单使用 resources:read／write 权限，配置步骤见[执行资源管理](EXECUTION_RESOURCES_R4.md)。资料集用途见[年报参考](ANNUAL_REPORTS_R5.md)。

## 原生任务取消后的恢复核验

对已回传 `RUNTIME_FAILED` 的任务，恢复输入包含后端核验结果：失败任务无 RESERVED／RUNNING 尝试、仓库无 HELD／UNKNOWN 写入锁、原来源具备当前项目授权。任何一项不满足，程序直接阻止恢复，不让模型豁免。

这些事实与原始失败报告一并保存在新的阶段输入中，旧 WAIT 决定保持可查；新的模型决定仍经过现有预算门禁，不扩大预算、范围、检查或权限。只有后端恢复角色决定 RETRY 才按原有限版本边界创建新任务、新尝试和新放置；不会恢复旧租约，也不是产品验收或合并授权。当前办公 Mac 仍按 DEVELOPMENT_FUNCTIONAL 记录，不把客户端已停止回执升级为受控宿主证明。

## 修复后的有限恢复

原始运行时恢复仍以问题版本 1–4 为限，不删除四次失败报告、不重置计数。版本 4 因 `RUNTIME_FAILED` 停止后，可通过 `POST /api/v1/maintenance/automation/problems/{id}/runtime-repair` 登记 `{expectedVersion:4,evidenceDigest:"<sha256>"}`。登记只创建 PENDING 记录，不启动任务、批准候选或合并；相同请求幂等，同一问题的同一修复类别只允许登记一个摘要。租期修复类别为 `LEASE_RUNTIME`；后续模型传输类别另受下述版本与前置证据限制。

发布流水线在后端受保护的只读目录登记 `funnywork.runtime-repair/v1` 发布清单，文件名为清单字节的 SHA-256 加 `.json`，相邻 `<artifactSha256>.zip` 是对应签名安装包。用 `FUNNYWORK_MAINTENANCE_REPAIR_EVIDENCE_DIRECTORY` 指定该目录，并只读挂载到业务服务；不要允许办公客户端、候选工作区或反馈接口写入。清单绑定仓库、问题/版本、源码 SHA、安装包 SHA、原同步设备、其策略设备 ID、客户端版本、签名/公证与回归检查、签发及不超过七天的到期时间。登记失败不授权执行。

`sourceSha` 保持为安装包实际构建提交；当修复已包含在更晚的发布中，可另填完整的 `repairSourceSha`。后端独立读取 GitHub 的两个提交及 compare 接口，要求修复提交是构建提交的祖先，读取完整修复补丁并核验其中包含回归测试，再把两份补丁交给恢复审查。分叉、倒退、不完整补丁或缺失回归测试均拒绝；没有该字段时仍核验构建提交自身的修复与测试，不改变一次恢复限制。

提交比较仅放行无请求体的 GET，且两端必须是完整提交 SHA；通用路径穿越防护继续生效。只读证据验证器升级时，按程序内固定版本追加证据检查阶段；旧失败阶段及其计数保持原样，不重置客户端执行或恢复次数，也不自动重复模型审查或外部写入。

清单可用 `releaseChecks.regressionLogSha256` 绑定回归日志名称与 SHA-256；发布流水线把日志存为只读注册目录中的 `<sha256>.log`，后端重新计算摘要后才交给审查。旧执行器摘要缺少错误分类时，后端另从原设备、失败问题版本及租约代际对应的已认证同步会话读取最后一次终态，只提供安全错误代码与事件序号。该历史仍是客户端来源的开发环境证据，不能当作硬件证明；前一轮失败检查必须在新候选上全部重跑。

后端重新计算清单和安装包摘要，从固定 GitHub 仓库读取准确提交的完整补丁及回归测试，核验原任务已停止、无 HELD/UNKNOWN 仓库写者、当前项目授权、原设备已重启且在线，以及策略回执版本与发布清单一致。策略回执是客户端声明，由后端关联观察，不是硬件证明；此流程仅适用于已有 `DEVELOPMENT_FUNCTIONAL` 策略。受控交付仍需独立可信的执行证据，不能把办公 Mac 的发布验证表述成受控环境证明。

后端 `REPAIR_REVIEW` Agent 根据已获取的修复补丁、回归证据和失败原因作 RESTORE／WAIT／REJECT 判定。RESTORE 在事务中重新核验停止、授权、设备及问题版本，再只建立一次新的版本 5 开发任务，绑定已修复的原设备及版本；领取、续租和回传继续检查绑定及原授权。部署或服务重启、重复登记、重复轮询不能为同一修复类别生成第二个恢复任务。新任务再次失败即保持阻塞；仅经过独立证据审查的不同模型传输修复可按下述限制再恢复一次，既有四次上限与已消耗的修复记录均不重置。候选仍须经过固定 SAT／UAT、独立代码审查、产品验收及后端受控合并和 Issue 回告关闭；恢复决定本身不授予交付权限。

### 模型传输修复与有限恢复

原始四次自动执行与租期修复后的失败均保留。模型传输故障通过同一接口登记 `{expectedVersion:5,evidenceDigest:"<new sha256>"}`，采用单独的 `MODEL_TRANSPORT` 修复证据，关联已经消耗的 `LEASE_RUNTIME` 证据；V113 保留原行，只把唯一约束改为“问题＋修复类别”。每类最多一次，传输恢复后不再增加后续恢复窗口。原始 `version < 4` 自动重试限制不变。

后端核验新签名公证版本、制品摘要、独立拉取的源码补丁、传输回归与真实连接探测，检查旧执行已停止、写者已释放、当前设备授权；旧模型许可只接受 SUCCEEDED／FAILED／CANCELLED／EXPIRED 终态，等待、运行、停止中、未知及未识别状态均阻止恢复。随后由后端 Agent 决定恢复或拒绝。恢复只生成候选开发任务，仍必须经过固定 SAT／UAT、独立审查、自动验收和后端合并回告；没有人工批准入口，不重置额度或删除失败历史。

客户端许可申请响应丢失时只核对同一调用 ID、摘要和额度的一张许可；执行请求不重发。连接、许可响应、执行与读流分别记录安全错误分类，禁止凭错误文本直接启动新的模型执行。交付状态通过后端记录的实际 PR、验证结果、合并和 Issue 回告查询。

只读恢复审查若因服务进程中断而失联，必须等原阶段租约和模型执行期限均过期，再由管理员通过原模型对账接口确认停止、保守结算并留下审计。后端只把相同策略、设备问题版本的此类已对账调用作为新证据追加审查；原 BLOCKED 阶段不重置，最多允许两次此类补充，不适用于开发执行、验证或交付写入。

模型预算不足属于准入等待，未发出模型调用时不消耗模型阶段重试次数。恢复审查输入绑定当时的全局预算上限；管理员通过原接口改变上限后可追加审查输入，旧预算失败记录保留。此行为不会自行提高预算、授信或修改实际费用。

代码审查只接收实际候选源码与明确标为提交前的开发检查状态摘要，不把命令输出中的旧 HEAD 或冻结来源基线当作精确候选验证。开发原始输出继续完整保存在报告与审计证据中。代码门通过后仍须对精确候选 SHA 独立运行全部冻结 SAT/UAT，再进入产品验收和交付；摘要不授予验收权限。


### 自动化概览的范围与分页

概览的后端阶段和风险记录先按当前身份可访问的仓库过滤，再分别取最新 200／100 条；没有匹配范围时返回空列表。相同时间戳按 ID 稳定排序。

### 产品条件来源校验

对有结构化客户端期望的反馈，新增程序约束识别其中未要求、却由模型新增的基线测试通过条件；拒绝依据单独持久保存，并允许产品角色在原范围内重规划一次。仍有此问题则在需求冻结及派发前保持待澄清，不创建执行任务。明确要求的基线不变式、基线失败而候选通过、旧版非结构化文本分别处理；该规则只覆盖已列出的条件表达，不声称解决任意语义矛盾。管理端将该阶段显示为“验收条件校验／重新规划”。产品提示同时明确实际观察与复现信息不能擅自转成成功条件。

基线通过条件的来源校验同时检查生成的需求正文、验收摘要与逐项条件，避免正文中的错误要求进入冻结需求。显式“不要求通过／不要求退出码 0”不当作通过要求；同一句中先描述候选、后追加基线通过要求时，继续检查基线部分。该规则识别已覆盖的表达，独立产品审查继续检查完整需求。
